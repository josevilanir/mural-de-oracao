# Phase 2: Audit Logging - Research

**Researched:** 2026-03-21
**Domain:** Prisma schema extension, database audit trail, Next.js server actions
**Confidence:** HIGH

## Summary

This phase adds a durable, queryable audit trail to the database. Every admin moderation action (hide/approve prayer, approve/reject group) and every group management action (create, delete, membership changes) must write a row to an `AuditLog` table. The application is a Next.js 14 app using Prisma 7 with a Neon PostgreSQL backend.

The approach is simple and well-suited to this codebase: add a single `AuditLog` Prisma model, generate and run a migration, then call `prisma.auditLog.create()` inside each affected server action — either alongside the existing `prisma.$transaction()` block or as an additional step. No external library is needed. The audit log must not use ephemeral storage; writing to the same PostgreSQL database as the rest of the schema satisfies the durability requirement.

The scope is narrow: seven server actions across two files (`app/actions/admin/moderation.ts` and `app/actions/groups/index.ts`) each need one additional write. The Prisma schema needs one new model. No UI is required by the requirements.

**Primary recommendation:** Add one `AuditLog` Prisma model, one migration, and `prisma.auditLog.create()` calls inside each of the seven affected server actions using the existing `prisma` singleton.

## Architecture Patterns

### Pattern 1: AuditLog Prisma Model

**What:** A single append-only table with actor, action type, timestamp, and optional target references.

**When to use:** Every successful mutation of a moderated or managed resource.

**Example:**
```prisma
// Source: Prisma official docs — https://www.prisma.io/docs/orm/prisma-schema/data-model/models
enum AuditAction {
  PRAYER_HIDDEN
  PRAYER_APPROVED       // un-hidden
  GROUP_APPROVED
  GROUP_REJECTED
  GROUP_CREATED
  GROUP_DELETED
  JOIN_REQUEST_SUBMITTED
  JOIN_REQUEST_APPROVED
  JOIN_REQUEST_REJECTED
  PRAYER_REMOVAL_APPROVED
  PRAYER_REMOVAL_REJECTED
}

model AuditLog {
  id        String      @id @default(cuid())
  action    AuditAction
  actorId   String
  targetId  String?     // prayerId, groupId, or memberId depending on action
  createdAt DateTime    @default(now())

  actor User @relation(fields: [actorId], references: [id])

  @@index([actorId, createdAt])
  @@index([createdAt])
}
```

`User` will need a back-relation:
```prisma
// In the existing User model, add:
auditLogs AuditLog[]
```

### Pattern 2: Inline Audit Write in Server Action

**What:** After a successful database mutation, write an audit log row.

**When to use:** Every server action callsite where a mutation succeeds.

**Example:**
```typescript
// Source: project convention from app/actions/admin/moderation.ts
export async function toggleHiddenAction(prayerId: string, isHidden: boolean) {
  const session = await auth();
  // ... auth check ...

  try {
    await prisma.prayer.update({
      where: { id: prayerId },
      data: { isHidden },
    });
    await prisma.auditLog.create({
      data: {
        action: isHidden ? "PRAYER_HIDDEN" : "PRAYER_APPROVED",
        actorId: session.user.id,
        targetId: prayerId,
      },
    });
    revalidatePath("/admin/prayers");
    revalidatePath("/");
    return { success: true };
  } catch (err) {
    console.error("[toggleHiddenAction]", err);
    return { success: false, error: "Algo deu errado." };
  }
}
```

### Pattern 3: Atomic Audit Write Inside Existing Transaction

**What:** Where an action already uses `prisma.$transaction([...])`, add the audit log create to the same transaction array to guarantee atomicity.

**When to use:** `deleteGroup` and `resolvePrayerRemoval` — both already use `prisma.$transaction`.

**Example:**
```typescript
await prisma.$transaction([
  prisma.prayer.deleteMany({ where: { groupId } }),
  prisma.group.delete({ where: { id: groupId } }),
  prisma.auditLog.create({
    data: {
      action: "GROUP_DELETED",
      actorId: session.user.id,
      targetId: groupId,
    },
  }),
]);
```

### Anti-Patterns to Avoid

- **Writing audit log before the mutation succeeds:** If the main write fails, the audit row is orphaned and wrong. Always write audit after confirming success, or inside the same transaction.
- **Using a non-relational field for actorId:** The actor must be a valid `User.id` so the relation constraint enforces referential integrity.
- **Soft-deleting or updating audit rows:** The table is append-only. Never add an `updatedAt` or `isDeleted` field.
- **Logging failed attempts:** Only log successful mutations. Logging failures creates noise and is not required.

## Don't Hand-Roll

| Problem | Don't Build | Use Instead | Why |
|---------|-------------|-------------|-----|
| Enum for action types | A freeform `String action` column | Prisma `enum AuditAction` | Enum enforces validity at schema level, prevents typos, enables indexed queries |
| Migration | Manual SQL | `prisma migrate dev --name add_audit_log` | Prisma tracks migration state, generates idempotent SQL, handles rollback tracking |
| Timestamp | Application-level `new Date()` | `@default(now())` in schema | Database-side timestamp avoids clock skew across serverless instances |

**Key insight:** The entire audit logging system is a schema addition plus seven one-liner `prisma.auditLog.create()` calls. Do not over-engineer this.

## Common Pitfalls

### Pitfall 1: Missing Back-Relation on User Model

**What goes wrong:** Prisma schema validation fails: "AuditLog has a relation to User, but User has no corresponding relation field."

**Why it happens:** Prisma requires both sides of a relation to be declared.

**How to avoid:** Add `auditLogs AuditLog[]` to the `User` model when adding the `AuditLog` model.

**Warning signs:** `prisma validate` or `prisma migrate dev` errors mentioning missing relation fields.

---

### Pitfall 2: Audit Write Outside Transaction Causes Inconsistency

**What goes wrong:** The main mutation succeeds, then an error (network, DB) prevents the audit write. The audit log is missing an entry, but no error is returned to the client.

**Why it happens:** Two sequential awaits are not atomic.

**How to avoid:** For actions that already use `prisma.$transaction`, include the audit create in the same transaction array. For simple single-write actions, the risk is low because both operations target the same Neon connection and same database — acceptable for this use case. Full atomicity is only critical for the delete/removal-resolution paths.

**Warning signs:** Audit log has gaps corresponding to high-traffic periods or connection timeouts.

---

### Pitfall 3: Session User ID Not Verified Before Audit Write

**What goes wrong:** `session.user.id` is `undefined`; `prisma.auditLog.create` throws a foreign key constraint violation on `actorId`.

**Why it happens:** Auth check happens before the try block but the `session` variable is used inside it without re-checking.

**How to avoid:** The existing pattern in `moderation.ts` calls `requireAdmin(session)` which throws if `session?.user?.id` is missing. The audit write happens inside the success path after that guard, so `session.user.id` is guaranteed. Follow the same pattern in `groups/index.ts` where each function already has an early return guard.

**Warning signs:** Prisma foreign key constraint errors in logs referencing `AuditLog.actorId`.

---

### Pitfall 4: Forgetting `prisma generate` After Schema Change

**What goes wrong:** TypeScript compilation fails — `prisma.auditLog` does not exist on the client type, `AuditAction` enum is not found.

**Why it happens:** The Prisma client is generated from the schema; editing `schema.prisma` alone does not update the client types.

**How to avoid:** Run `prisma migrate dev --name add_audit_log` (which calls `generate` automatically) or run `prisma generate` explicitly after schema changes.

**Warning signs:** TypeScript errors referencing missing properties on the `PrismaClient` type.

## Open Questions

1. **Should `requestJoinGroup` (member status: PENDING) be logged under AUDT-02?**
   - What we know: AUDT-02 says "membership changes." A pending join request is the start of a membership change.
   - What's unclear: The requirement lists "create, delete, membership changes" — "pending join request submitted" is arguably a membership change.
   - Recommendation: Log it with `JOIN_REQUEST_SUBMITTED`. If it is later approved or rejected, those actions are logged separately. This gives the fullest picture and costs one extra enum value.

2. **Should `targetId` be typed more specifically (separate `prayerId`/`groupId`/`memberId` columns)?**
   - What we know: A single `targetId String?` works for querying "what was acted on."
   - What's unclear: Querying "all audits for group X" across pray/group/member actions is harder with a single field.
   - Recommendation: Single `targetId` is sufficient for this phase. The requirements do not specify query patterns beyond "queryable." If a future phase needs filtering by resource type, separate columns or a `targetType` discriminator can be added then.
