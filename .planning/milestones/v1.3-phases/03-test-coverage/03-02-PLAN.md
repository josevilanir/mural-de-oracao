// Login uses NextAuth's signIn("credentials", { email, password }) on the client.
// The authorize() function inside CredentialsProvider handles validation:
async authorize(credentials) {
  if (!credentials?.email || !credentials?.password) return null;
  const user = await prisma.user.findUnique({ where: { email: credentials.email as string } });
  if (!user || !user.password) return null;
  const isValid = await bcrypt.compare(credentials.password as string, user.password);
  if (!isValid) return null;
  return { id: user.id, email: user.email, name: user.name, image: user.image, role: user.role };
}
// There is NO loginAction server action. To test login, extract and test the authorize logic
// by importing the NextAuth config or by testing the credential validation behavior
// through the exported auth/signIn functions.

Create `tests/actions/auth.test.ts` testing all auth-related server actions AND the NextAuth credential login flow.

**Important context:** There is NO `loginAction` server action. Login is handled by NextAuth's `CredentialsProvider` `authorize()` function in `lib/auth.ts`. To test login, we test the `authorize` behavior indirectly: the same credential validation logic (prisma.user.findUnique + bcrypt.compare) is what gets exercised. We can test this by extracting the authorize function's behavior through the NextAuth configuration, or more practically, by testing the credential validation path that `authorize` follows.

The recommended approach: since `lib/auth.ts` exports `{ handlers, auth, signIn, signOut }` from `NextAuth(config)`, and the `authorize` function is inline in the config, the cleanest way to test login credential validation is to replicate the authorize logic in tests -- mock `prisma.user.findUnique` and `bcrypt.compare`, then call `signIn` or directly test the authorize path. However, since `signIn` from next-auth triggers HTTP internals that are hard to unit test, the practical approach is:

**Test the credential validation logic by testing what authorize() does:** mock prisma and bcrypt, then verify the expected behavior by calling the authorize-equivalent flow. Since we cannot easily extract `authorize` from the NextAuth config, create a `describe("login (NextAuth authorize)")` test suite that tests the same prisma + bcrypt calls that authorize makes, validating:
- Missing credentials returns null (no user returned)
- User not found returns null
- OAuth user (no password) returns null
- Invalid password returns null
- Valid credentials returns user object

Implementation: Import `prisma` and `bcrypt` mocks. For each test, set up the mocks as authorize() would encounter them, then verify the behavior by calling the mocked functions directly in the same sequence authorize does. This validates the credential validation logic even though we're not calling authorize() directly.

Alternatively (and preferably), read `lib/auth.ts` at execution time. If the `authorize` function can be extracted by importing the NextAuth config options before they're passed to `NextAuth()`, do that. If `lib/auth.ts` directly calls `NextAuth({...})` and exports only the result (which it does), then use the mock-sequence approach described above.
